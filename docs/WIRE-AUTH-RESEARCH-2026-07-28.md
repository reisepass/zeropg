# Wire layer and auth: research dossier, 2026-07-28

Raw output of a parallel research fan-out run while planning a real Postgres wire frontend
(TLS + SCRAM) and a credential model able to stand next to Neon and Supabase. Four research
tracks completed; a fifth (pglite-socket internals vs PGlite's protocol surface) and the
design/critique phases were still running when this was written, so **this file is evidence,
not conclusions.** Decisions live in
[CONNECTION-SECURITY-AND-WIRE.md](CONNECTION-SECURITY-AND-WIRE.md).

## The three findings that change the plan

1. **pg-gateway already exists in this repo and is already spiked.** MIT, by Greg Richardson
   (supabase-community), a full server-side Postgres v3 frontend with SSLRequest/TLS upgrade
   and trust/md5/scram-sha-256 auth. It is already a root devDependency at `^0.3.0-beta.4`,
   already exercised at `experiments/prisma-spike/pggw.ts`, and `docs/ORM-ADAPTER-NOTES.md:255-262`
   already concluded it is "the better wire layer for everything else" and named the swap as
   a candidate follow-up. **Build-vs-adopt is close to settled: adopt.**
2. **The SSLRequest fix exists upstream.** pglite-socket 0.2.3 added `handleSslRequest()`
   replying `'N'`. The monorepo pins `^0.2.2`, which lacks it. Peer ranges already permit the
   bump. GSSENCRequest is still unhandled even in 0.2.4.
3. **The single biggest regression risk in any wire swap** is pglite-socket's
   transaction-aware `QueryQueueManager`. That is what makes RLS isolation safe on the shared
   session (proven: 2s held transaction + 100 concurrent cross-user reads, zero bleed). It has
   never been tested against pg-gateway. Any swap must re-verify it first.

Also settled and NOT to be redone: per-connection prepared-statement namespacing was
assessed against source as a deep architectural change, not a patch; `DISCARD ALL` at
connection close is unsafe because it nukes a concurrent peer's statements; true
session-per-connection is impossible on PGlite.

## PRIOR ART IN THE ZEROPG REPO

The zeropg repo has months of settled design work across all four areas you asked about; almost nothing here needs redoing.

**(a) Wire layer / pglite-socket.** The architecture is fixed: PGlite is one Postgres session, and `@electric-sql/pglite-socket`'s `PGLiteSocketServer` multiplexes every TCP connection onto it (`packages/client/src/wire.ts`, `packages/server/src/server.ts:158-168`). This is a *throughput* limit, never a correctness one (measured: Pool(10) × 20 overlapping queries = exactly serialized, 1033ms). Consequences already characterized and documented: read-after-write can lag seconds behind an HTTP 200; `COPY ... FROM STDIN` is not carried and wedges the session with FATAL `08P01`; session GUCs (`search_path`, `SET ROLE`) leak across connections; an idle-open explicit transaction freezes *every* client; server-side `statement_timeout` is inert on PGlite. The one property that makes RLS safe is pglite-socket's transaction-aware `QueryQueueManager`. `pg-gateway` was already spiked as an alternative wire layer (`experiments/prisma-spike/pggw.ts`) and judged better for everything except `prisma migrate dev` — a documented candidate follow-up, not done.

**(b) Auth / passwords / TLS.** Decided and written down: **zeropg has no built-in auth anywhere; the wire accepts any username/password, and every security property comes from network placement plus gates in front of it** (docs/EDITOR-AUTH-SECURITY.md:18-21). `@zeropg/server`'s HTTP `/sql` is unauthenticated by construction; the CLI actively warns that an `allUsers` invoker binding is an open SQL endpoint. The console is loopback-only and refuses to widen; the one wide-bound mode (`--inspector`) uses a single 192-bit bearer token → `zpt` cookie, with structural route pruning and read-only detached replicas. The hardening ladder (IAM identity → per-link HMAC `{target,exp}` → PII redaction) is already specced with the `ConsoleAuth` interface shaped for the third mode. No TLS on the wire, ever, by design — `sslmode=disable` everywhere.

**(c) Prepared statements.** Fully characterized. The wall is *named* server-side prepared statements (`42P05`). Screen: "does the driver name its server-side prepares and keep them across pooled connections?" Blocked with no escape hatch: Rust sqlx, Rust Diesel. Escape hatches found and verified: pgx v5 `cache_describe` (NOT `simple_protocol` — it breaks JSONB with `22P02`), pgx v4/pop `statement_cache_mode=describe`, PostgREST `db-prepared-statements=false` + pool=1.

**(d) Topology.** Loopback wire + HTTP control face; raw 5432 never exposed on Cloud Run; migrations applied by the single writer to itself; graduation is `pg_dump`.

Two things were **explicitly assessed as too hard**: per-connection prepared-statement namespacing in pglite-socket (needs a real wire-protocol parser — deep, not a patch) and session-per-connection (impossible, PGlite is single-session). I found several doc contradictions, the biggest being that the SSLRequest gap is already fixed upstream in pglite-socket 0.2.3.

## NEON MODEL

Neon's connection story is three separate faces over one proxy: the Postgres wire (TCP 5432), a WebSocket tunnel, and SQL-over-HTTP. All three converge on the same Rust proxy (github.com/neondatabase/neon/proxy), which authenticates and then dials the compute.

Connection string: `postgresql://alex:AbC123dEf@ep-cool-darkness-a1b2c3d4-pooler.us-east-2.aws.neon.tech/dbname?sslmode=require&channel_binding=require`. The only truly mandatory things are TLS itself and a resolvable endpoint id. The endpoint id is the first DNS label (`ep-cool-darkness-a1b2c3d4`); `-pooler` selects PgBouncer; port is 5432 for both. `sslmode=` and `channel_binding=` are client-side hints, not server requirements - you can delete `channel_binding=require` and connections still work (Neon added it to the default string in June 2025).

TLS is hard-required: "Neon rejects connections that do not use SSL/TLS", behaving like a pg_hba.conf with only `hostssl` records. `sslmode=disable` yields `connection is insecure (try using sslmode=require)`. `sslmode=prefer` (libpq's default) is not blocked - the server offers TLS so prefer upgrades - but Neon's own blog argues prefer and even require are near-worthless because neither authenticates the server; they compensate with SCRAM-SHA-256-PLUS channel binding, and advocate a new `sslmode=secure` (verify-full + system roots).

Auth: SCRAM-SHA-256 is the default password encryption for roles; the proxy also speaks SCRAM-SHA-256-PLUS. There is a documented downgrade path - if you smuggle the endpoint id into the password field (`endpoint=ep-x;password`), auth drops to cleartext `password` (still inside TLS). The WebSocket driver does the same by default (`forceDisablePgSSL: true`, `pipelineConnect: 'password'`). No client-certificate/mTLS support is documented anywhere.

SNI: the Postgres startup packet carries no hostname, so the proxy cannot know which compute to route to before auth. Neon reads TLS SNI. Clients without SNI get: `ERROR: The endpoint ID is not specified. Either upgrade the Postgres client library (libpq) for SNI support or pass the endpoint ID ... as a parameter: '&options=endpoint%3D'`.

Two auth layers, cleanly separated. Layer 1 is Postgres role auth (SCRAM/password, `neondb_owner`). Layer 2 is Neon Auth - now "Managed Better Auth" (Stack Auth is the legacy implementation, still supported) - which stores users/sessions in a `neon_auth` schema *inside your database*, issues a JWT with a `sub` claim, and never becomes a Postgres login. Instead the proxy/Data API validates the JWT against a JWKS and connects as the fixed `authenticated` or `anonymous` role, exposing identity to RLS via `pg_session_jwt`'s `auth.user_id()` / `auth.uid()` / `auth.session()`.

The answer to question 6 is unambiguously yes: Neon's HTTP `/sql` endpoint is fully parameterized. Body is `{"query": "...", "params": [...]}` (or `{"queries": [...]}` for a batch). The proxy deserializes params to `Vec<Option<String>>`, converting every JSON value to a Postgres *text* literal, then calls `query_raw_txt(query, params)` - so parameters are bound in text format with server-side type inference (no client-supplied type OIDs). Results come back as text with per-column `dataTypeID`, and node-postgres type parsers run client-side. Credentials travel in a `Neon-Connection-String` header; the endpoint id is parsed from that header URL's hostname, so SNI is irrelevant on the HTTP path.

## SUPABASE MODEL

Supabase exposes four Postgres endpoints, all with the SAME password but different hosts/ports/usernames: direct `postgresql://postgres:[YOUR-PASSWORD]@db.<ref>.supabase.co:5432/postgres` (IPv6-only unless you buy the IPv4 add-on); Supavisor shared pooler session mode `postgres://postgres.<ref>:[PW]@aws-<region>.pooler.supabase.com:5432/postgres` (IPv4, prepared statements OK); Supavisor transaction mode, same host on `:6543` (IPv4, "does not support prepared statements"); and a paid dedicated PgBouncer at `db.<ref>.supabase.co:6543`. The pooler encodes the tenant in the USERNAME (`postgres.<project_ref>`) because there is no per-tenant hostname. None of the connection strings Supabase ships contain an `sslmode` param.

TLS is OPTIONAL by default and this is deliberate: "Your Supabase project supports connecting to the Postgres DB without SSL enabled to maximize client compatibility." Their `pg_hba.conf` uses `host all all 0.0.0.0/0 scram-sha-256` (not `hostssl`), and `password_encryption = scram-sha-256`. A dashboard/API/CLI toggle ("Enforce SSL on incoming connections") flips it on (and reboots the DB). They DO ship a CA cert (`prod-ca-2021.crt`, downloadable from Database Settings → SSL Configuration) and document `sslmode=verify-full sslrootcert=...` as the recommended mode, but nothing forces you there. HTTP APIs (PostgREST/Auth/Storage) always enforce SSL.

Auth is three stacked layers that people constantly conflate. (1) Postgres role auth: the `postgres` superuser password is generated/typed at project creation, "for security reasons, your database password is never shown" again, and the only recovery is Reset Password in Database Settings; SCRAM-SHA-256 on the wire. (2) API-key layer answers "WHAT is calling" - publishable `sb_publishable_...` (legacy `anon` JWT) and secret `sb_secret_...` (legacy `service_role` JWT). (3) GoTrue/Supabase Auth answers "WHO", minting a short-lived per-user JWT whose `role` claim is literally "The Postgres role to use when applying Row Level Security policies." PostgREST connects as `authenticator` (very limited), verifies the JWT, and does `SET LOCAL ROLE` into `anon` / `authenticated` / `service_role`, exposing claims via `current_setting('request.jwt.claims')` which `auth.uid()`/`auth.jwt()` read. RLS is the actual enforcement; `service_role` has `BYPASSRLS`. So the key never becomes a Postgres password - it becomes a role switch.

For a naive `new Pool({connectionString: DATABASE_URL})`: it "works" in the worst way. `pg` defaults to `ssl: false`, and since Supabase's copied string has no `sslmode` and their hba allows non-SSL, you get a silent PLAINTEXT connection across the public internet with a superuser password. If you're on Vercel/GH Actions/most Docker and use the direct string you instead get `ENETUNREACH` (IPv6). If you "fix" it by appending `?sslmode=require`, pg-connection-string (non-libpq-compat, the default) sets `ssl = {}` with `rejectUnauthorized` left at Node's true, so verification runs against system roots and Supabase's private CA fails with SELF_SIGNED_CERT_IN_CHAIN - which the internet answers with `rejectUnauthorized: false`, i.e. back to unverified. And if you pointed at :6543 with a driver that names statements, you get prepared-statement errors.

## WIRE PROTOCOL v3 SERVER + EXISTING LIBRARIES

pg-gateway is real and it is the decisive finding: https://github.com/supabase-community/pg-gateway by Greg Richardson (gregnr), MIT, 260 stars, npm `pg-gateway`. It is a full server-side Postgres v3 frontend (framing, SSLRequest/TLS upgrade, startup params, auth) that hands post-auth bytes to a hook - exactly the shape needed to front PGlite, and its own examples front PGlite. But the maturity picture is split. `main` is frozen at v0.2.4 (July 2024) and only has cleartext/md5/cert auth; that stale README is what web search returns and why every summary claims "no SCRAM". The real code lives on the unmerged branch `next` (PR #21 "Next v0.3.0", open since 2024-09-13, 139 commits, 74 files), published only as `0.3.0-beta.4` on 2024-12-23 and untouched for 19 months. That beta DOES implement SCRAM-SHA-256 (auth/sasl/scram-sha-256.ts, 275 LOC + sasl-mechanism 39 + crypto 120), web/deno/node platform adapters, and SNI. It is not a toy: firebase-tools 15.24.0 depends on `pg-gateway@^0.3.0-beta.4`, driving 7.2M npm downloads/month (up from 1.4k in Jan 2025); windmill, netlify/primitives, nocodb/sql-control and supabase-community/database-build also use it. This repo already has it in devDependencies and already spiked it (experiments/prisma-spike/pggw.ts); docs/ORM-ADAPTER-NOTES.md already recommends swapping serveWire onto it.

I verified it live against real libpq (psql 18.4) with a self-signed CA, TLS, and scram-sha-256: sslmode=require works, sslmode=verify-full works, sslmode=disable is correctly rejected with 08P01, and a wrong password yields the standard FATAL "password authentication failed". sslmode=require validates nothing when no sslrootcert is given (self-signed accepted); with sslrootcert set it validates like verify-ca, per libpq's documented back-compat. channel_binding=require fails (only SCRAM-SHA-256 is advertised, never -PLUS) but that is harmless since libpq's default is `prefer`.

Three real defects found by probing. (1) A client that rejects the server cert (TLS alert unknown_ca) triggers an unhandled ERR_INVALID_STATE "WritableStream is locked" at connection.ts:228 and kills the whole Node process - reproducible, remote, trivially triggerable. (2) A protocol 3.2 startup (PG18 libpq with max_protocol_version=latest) hits `Unexpected initial message`; there is no NegotiateProtocolVersion. (3) It never sends BackendKeyData, and CancelRequest (80877102) falls into the same `Unexpected initial message` throw (it does close with zero bytes written, which is accidentally close to spec).

Q6 is settled empirically. I built the rewriter in ~45 lines over pg-gateway plus one shared PGlite: without it, connection B preparing `s1` fails with 42P05; with Parse/Bind/Describe/Close/Execute names prefixed per connection, both connections prepare `s1` and A's statement still resolves afterwards. Caveats: SQL-level PREPARE/DEALLOCATE bypass the rewriter (26000), and `pg_prepared_statements` exposes the prefixed name. Also note pg-gateway has zero cross-connection serialization - swapping serveWire off pglite-socket would lose its transaction-aware QueryQueueManager, which is what makes the Supabase RLS story safe today.

## PGLITE-SOCKET INTERNALS AND PGLITE PROTOCOL SURFACE

**What pglite-socket is.** 771 lines of TypeScript (`/Users/user/workspace/zeropg/node_modules/@electric-sql/pglite-socket/src/index.ts`), three classes, zero protocol knowledge. It is a length-prefix framer plus a serializing queue. The only protocol field it ever reads is `readInt32BE(4) === 196608` to guess "this is a 3.0 startup packet" (lines 351-368); every other message is framed as `1 + readInt32BE(1)` and forwarded verbatim to `db.execProtocolRawStream()`. It never inspects a message type byte, never parses a startup packet's key/value pairs, and never generates a single backend byte of its own (except the raw ASCII `"Too many connections\n"` at line 710, which is not even a valid protocol message).

**Where the handshake really comes from.** PGlite does it, in real Postgres C. `execProtocolRawSync` (pglite `src/pglite.ts:876`) branches on `message[0] === 0` to `#processStartupPacket` (line 1308), which calls `mod._ProcessStartupPacket(myProcPort, true, true)` - the genuine `ProcessStartupPacket()` with `ssl_done=true, gss_done=true` - then `_pgl_sendConnData()`. That emits a 429-byte block: `AuthenticationOk(0)`, 16 `ParameterStatus` messages (`server_version=18.3`, `client_encoding=UTF8`, `search_path=public`, `is_superuser=on`, ...), `BackendKeyData(pid=42, key=2875488)`, `ReadyForQuery('I')`. The WASM Postgres does 100% of the handshake; the shim does 0%.

**PGlite enforces nothing.** `{user:nosuchuser, database:nosuchdb, password:hunter2}` returns `AuthenticationOk` immediately; `current_user` is `postgres`, `current_database()` is `postgres`. Two startup packets with different user and different database produce byte-identical 429-byte responses. `options=-c search_path=... -c statement_timeout=1234`, `application_name`, and `client_encoding=LATIN1` are all silently discarded - a following `SHOW` returns `public`, `0`, empty, `UTF8`. BackendKeyData is a hardcoded constant.

**The answer to the gating question: yes, you can own auth entirely.** A brand-new PGlite answers `Query "SELECT 1"` correctly with no startup packet ever sent - it is already a logged-in single-user backend. There is no double-auth sequence because there is no auth. Two clean options: (a) never forward the startup packet and synthesize ParameterStatus yourself (what the pg-gateway spike at `experiments/prisma-spike/pggw.ts` does, faking `serverVersion: '16.3'`), or (b) better - forward one startup packet at boot, cache the real 429-byte block, strip `R`/`K`, rewrite the trailing `Z` to `'I'`, and replay it per connection so clients see PGlite's actual GUCs.

**What must never be forwarded.** SSLRequest reaching `execProtocolRaw` throws `ExitStatus: exit(1)` and permanently corrupts the WASM instance - the next startup packet throws `RuntimeError: null function or function signature mismatch` and the response stream desynchronizes. GSSENCRequest is identical. CancelRequest throws `Cannot process startup packet`. PasswordMessage `'p'` and unknown type `'q'` cause an infinite synchronous spin inside `_PostgresMainLoopOnce` that blocks the entire Node event loop - a 20-second `setTimeout` never fired and the process had to be killed. That is a remote, unauthenticated, one-packet DoS. The only reason zeropg survives today is that pglite-socket's framer mis-sizes those packets and buffers forever instead of forwarding them.

## DESIGN: CREDENTIAL AND AUTHENTICATION MODEL

**Verdict on the token: yes, it is redundant — delete it as a per-instance concept, keep it only at fleet scope.**

A zeropg instance is one database, one role (`postgres`), one writer. Every powerful face — the wire, POST /sql, POST /flush — confers exactly the same authority: arbitrary superuser SQL. Two secrets guarding one authority is not defence in depth, it is two things to leak, two things to rotate, and two ways for an agent to get it wrong. Collapse to **one credential per instance**: the Postgres role password. The wire verifies it with SCRAM-SHA-256; HTTP verifies the same password via `Authorization: Basic postgres:<pw>` (also accept `Bearer <pw>` — agents reach for it). One stored artifact serves both: the Postgres SCRAM verifier `SCRAM-SHA-256$4096:<salt>$<StoredKey>:<ServerKey>`. Given cleartext from Basic you recompute SaltedPassword -> ClientKey -> H(ClientKey) and constant-time compare against StoredKey. Neon is the precedent and it is decisive: their HTTP /sql takes a `Neon-Connection-String` header carrying the same role password as the wire. One credential, two faces, at scale.

The three real arguments against collapsing, and their disposition. (1) *Least privilege across faces* — a Prometheus scraper should not hold the superuser password. Real, but the answer is capability tiering, not a second secret: `/up`, `/healthz`, `/wake`, `/ready` stay **always unauthenticated** (they are the scale-to-zero primitive; a cold client must reach them before it has anything), with `bootError` redacted to a code when unauthenticated; `/metrics` and `/flush` require the credential, with `ZEROPG_METRICS_PUBLIC=1` as the documented escape. (2) *Independent revocation* — killing a leaked HTTP token without rotating the DB password. Weak here: one role, one database, nothing worth preserving across a rotation, and rotation is cheap. (3) *Cleartext-per-request* — Basic sends the password on every call, unlike SCRAM. This is the one genuine regression. Mitigate with TLS enforcement (reject credentials arriving with `X-Forwarded-Proto: http`), and **additionally accept** a deterministically derived form `base64url(HMAC(ServerKey,"zeropg-http-v1"))` — verifiable from the stored verifier, irreversible to the password, no storage, no rotation of its own. Accept it in M1; do not require it.

**Where the token survives:** the console/inspector. Its principal is a human in a browser spanning N databases; there is no per-database credential to present without either sharing one password fleet-wide (terrible) or prompting per DB (kills one-click). So `INSPECTOR_TOKEN` stays, re-scoped as a *fleet-console* credential, and takes the already-specced third rung: per-link HMAC over `{target, exp}` signed by a fleet key. Rename it so nobody confuses it with instance auth. `/rest` also keeps its own model (PostgREST JWT + RLS). Rule: `/rest` answers if **either** a real `PGRST_JWT_SECRET` is configured (its model governs, no Basic gate) **or** the request carries the instance credential **or** `ZEROPG_REST_ANON=allow` is explicit. Neither -> 401 naming both routes.

**Provisioning precedence (boot decision tree).** 1. `ZeroPGServerOptions.password` (code wins). 2. `ZEROPG_PASSWORD_FILE` — covers K8s/Docker/Cloud Run secret-as-file. 3. `ZEROPG_PASSWORD` env. 4. Bucket-managed `auth.json` at the prefix root. 5. `ZEROPG_AUTH=trust` (explicit only). If 1-3 yield a password, compute the verifier and CAS it into `auth.json` so bucket and env can never drift (a mismatch on the next boot is a rotation, not an error). If none, GET `auth.json`; if present, use its verifier. If absent and the store is writable, mint 192 bits, PUT `auth.json` with if-none-match (create-only CAS, the same primitive as the manifest — first writer wins, losers re-GET), and write the cleartext to a **single-read claim object** `auth.claim.json` that `zeropg fleet credential <name>` GETs-then-DELETEs, expiring after `ZEROPG_CLAIM_TTL` (default 24h). Never print the password to stdout — Cloud Logging is readable by `roles/logging.viewer` for 30 days. If the store is read-only and no credential resolves: fail closed unless loopback-only. Note `collectGarbage` only walks `generations/`, so root-level `auth.json` and `auth.claim.json` are safe from GC.

**Reject two candidates outright.** Platform secret-manager SDKs inside the server: every platform is a dependency plus an IAM surface, and Cloud Run and K8s already project secrets into env or files, which is (2)/(3). Derivation from bucket credentials: the remote client has no bucket credentials to derive from, and on Cloud Run the bucket credential is a rotating metadata OAuth token — there is no stable long-lived key. Dead.

**Stress-testing "the bucket already has the whole DB".** The argument fails four ways if you store *cleartext*. (a) Bucket read gives you the database as of the last commit, offline, no lease; a live password gives you **write** to the primary. Storing cleartext escalates read -> write. (b) The inspector SA holds bucket *read* on every fleet prefix — cleartext there converts the deliberate asymmetry ("the wide-bound surface holds only disposable read-only copies") into a fleet-wide write compromise. That is literally the line EDITOR-AUTH-SECURITY.md says not to cross. (c) `fleet export`, `gsutil cp -r`, archive copies, cross-region replication and backups are designed to carry data, not credentials, and have different retention rules; a dump handed to a contractor would contain the production password. (d) GCS uniform bucket-level access has no per-prefix IAM, and `scripts/deploy.sh` puts every service in **one bucket** under a per-service prefix — a single `objectViewer` grant is every instance's password. **Therefore: store the verifier, never the password.** A SCRAM verifier is not password-equivalent (StoredKey is a one-way image of ClientKey), so bucket read grants nothing new against a 192-bit random secret and the original argument is restored. Corollary: user-supplied passwords are never written (offline-crackable, and the user already has them) — only their verifiers, and only because the CAS'd copy is what makes rotation and drift detection work.

**Fail-closed matrix.** Loopback bind + no credential -> start in trust mode, one WARN (preserves every current example and the PostgREST sidecar). Loopback + credential -> enforced everywhere except the always-open health/wake tier. **Non-loopback + no credential -> refuse to start, exit 78**, message naming the env var and the escape. Non-loopback + credential, HTTP -> start (the platform terminates TLS); reject credentialed requests over cleartext. **Non-loopback wire + credential but no TLS -> refuse** (SCRAM protects the password but not the data, and without channel binding does not authenticate the server; Neon's posture, not Supabase's). `ZEROPG_AUTH=trust` + any non-loopback bind -> refuse. The single escape everywhere is `ZEROPG_ALLOW_INSECURE_BIND=i-understand` — a *value*, not a boolean, so it cannot be set by typo and it greps. When it fires, `/ready` and the landing page carry `"insecure": true` and the fleet CLI renders it red. `wireHost=0.0.0.0` with no credential is the worst case in the system and becomes a hard refusal. `--allow-unauthenticated` stays in deploy.sh: public one-click URLs are the product; the fix is the app-level credential, not IAM.

**Rotation.** `auth.json` carries `{current, previous, previousExpiresAt, epoch}`; both verifiers authenticate during a default 1h overlap — the zero-downtime rotation Neon gets from parallel roles, cheaper because we have one role. Instances re-read `auth.json` at boot (they die constantly, so most pick it up for free) and on an authenticated `POST /reload-credential`, so no roll is needed. Writing `auth.json` needs bucket *write* IAM, which the operator has and the read-only inspector does not — the existing IAM boundary does the authorization, no new trust boundary and no control plane. Rotation must never roll a sleep-durability instance without `POST /flush` first (known write-loss path). Recovery of a lost password is a reset, never a reveal: Supabase's "never shown again" and Neon's reset endpoint are both right; Supabase's TLS-optional default and sslmode-less connection strings are both wrong and we copy neither.

**Fleet CLI so no human or agent hand-writes a secret:** `fleet credential <name>` (claim-once; `--json`, `--env`, `--write-env .env.local`; emits `postgres://postgres:<pw>@host/postgres?sslmode=require` and the matching `https://` + `Authorization` header form), `fleet password reset|set <name> [--overlap 1h] [--from-stdin]`, `fleet url --wire|--http|--psql|--no-credential`, `fleet status` showing auth mode / TLS / bind / epoch / overlap remaining, and `fleet doctor`, which actively probes every service for an unauthenticated `POST /sql` and a wrong-password wire accept. `doctor` is the regression net that proves the MongoDB default is gone.

### Rejected alternatives

- **Keep a first-class HTTP bearer token (ZEROPG_AUTH_TOKEN) alongside a Postgres password** - Two secrets guard one authority — arbitrary superuser SQL — on faces that are interchangeable. It doubles the leak surface, doubles rotation, and is exactly the ambiguity that makes an agent guess wrong ('which one do I put in DATABASE_URL?'). Neon proves the collapse works: the same role password authenticates both the wire and HTTP /sql.
- **Store the auto-generated password in cleartext in the bucket next to manifest.json** - Breaks the 'bucket read already gives you everything' argument in four places: it escalates bucket READ to database WRITE; the inspector SA has fleet-wide bucket read, so it would gain fleet-wide write; exports/backups/replication would start carrying live credentials with data-shaped retention; and GCS uniform bucket-level access has no per-prefix IAM while deploy.sh shares one bucket across all services. Store the SCRAM verifier instead, plus a single-read expiring claim object for the first handoff.
- **Derive the credential from the bucket credentials (HKDF over the storage key)** - The remote client has no bucket credentials to derive from — that is the whole point of the remote face. And on Cloud Run the bucket credential is a rotating metadata OAuth token, so there is no stable long-lived input. It only works when everyone already shares the bucket key, which is the case where you did not need a password.
- **Integrate a platform secret manager SDK (Secret Manager / Vault / AWS SM) into @zeropg/server** - Adds a per-platform dependency and a new IAM surface inside the server for zero capability gain: Cloud Run, Fly, K8s and Docker all already project secrets into env vars or files, which the ZEROPG_PASSWORD / ZEROPG_PASSWORD_FILE sources cover. Keep the secret-manager integration in the fleet CLI, where it is a deploy-time concern.
- **Solve exposure with IAM only — drop --allow-unauthenticated and require Google identity** - It works, but it kills the product: one-click public URLs and curl-from-anywhere are what makes zeropg demoable, and it does nothing for Fly/self-hosted or for the wire port. Offer it as a hardening rung, not the default. The default must be app-level auth.
- **mTLS / client certificates on the wire** - Neither Neon nor Supabase document client-cert auth, and no mainstream ORM setup path uses it. It requires distributing and rotating per-client key material with no control plane to do it — precisely the thing FLEET.md says is deliberately not built.
- **JWT (Supabase-style) for POST /sql** - JWT buys per-user identity and RLS role switching, which /sql cannot use — it runs as the single superuser by construction. That model belongs to /rest, where PostgREST already implements it. Putting JWT on /sql adds a signing key, a clock dependency, and an expiry story for zero authorization gain.
- **Keep pglite-socket and put auth in a TCP proxy in front of it** - A front proxy would have to terminate TLS and SCRAM, then speak an unauthenticated startup packet to pglite-socket — meaning it already implements the whole wire server, so the proxy IS the replacement. Worse, pglite-socket's own framer hangs on SSLRequest/GSSENCRequest/CancelRequest/protocol-3.2 and forwards unknown message types straight into a PGlite infinite spin; a front proxy does not fix any of that.
- **Auto-generate a password into memory at boot when none is configured** - Non-deterministic across restarts, and zeropg instances die constantly. Every cold start would invalidate every client's credential. Auto-generation is only acceptable when it is persisted (bucket auth.json) — never ephemeral.
- **Multiple Postgres roles with per-app least privilege now** - PGlite is a single session with is_superuser=on; SET ROLE leaks across the multiplexed session outside a transaction, and RESET ALL does not clear it. Role separation is unsound until per-connection session state exists. Ship one credential now; add a read-only second verifier once the wire replacement owns per-connection GUCs.
- **md5 password auth on the wire (simpler than SCRAM)** - Deprecated upstream, disabled by default in modern clients and distros, and password-equivalent at rest — which would destroy the whole 'the bucket only holds a verifier' property that makes bucket-managed credentials safe.

### Risks

- Fail-closed boot is a behavioural breaking change shipped in a patch bump. Every currently deployed service (11 public demos, the nightly-reset job, the inspector, every examples/cloudrun stack) binds HTTP non-loopback with no credential and will refuse to start on upgrade. Needs a staged rollout: 0.1.1 warns loudly and sets `insecure:true` in /ready, 0.2.0 refuses — or 0.1.1 refuses only when ZEROPG_HTTP_HOST is set explicitly. Decide before writing code, not after.
- M3 depends on pg-gateway, which is a beta that has not shipped in 19 months, whose 0.3.0 line has never been merged (PR #21 open since 2024-09-13), and which has a remote, trivially triggerable process kill on a TLS unknown_ca alert. Vendoring is mandatory, and vendoring means owning SCRAM correctness forever.
- Losing pglite-socket's transaction-aware QueryQueueManager silently breaks RLS isolation — the property the whole Supabase-on-zeropg story rests on. pg-gateway has zero cross-connection serialization. If the queue port is subtly wrong, the failure is cross-user claim bleed under concurrency, which no unit test catches by accident. test/killswitch-rls-isolation.mjs must gate the merge.
- HTTP Basic sends the full password on every request. A misconfigured logging middleware, an APM agent capturing headers, or a debugging proxy captures the live superuser credential. The derived HMAC form mitigates it but is optional by design, so most deployments will send cleartext-inside-TLS.
- auth.claim.json puts the cleartext password in the bucket for up to 24 hours. During that window every failure mode identified in the stress test (inspector SA read, backup copies, bucket-wide objectViewer) applies at full strength. The TTL and the single-read delete must be enforced by the server, not merely documented, and a bucket lifecycle rule should be the backstop.
- pg-gateway's SCRAM omits SASLprep (RFC 4013) password normalization, so any non-ASCII password will fail to interoperate with real Postgres clients. Auto-generated passwords must be ASCII base64url only, and user-supplied non-ASCII passwords must be rejected at set time with a clear error, not accepted and then mysteriously failing at connect.
- Its SCRAM has only ever been tested against node-postgres' own SASL client in memory. pgx, pgjdbc and sqlx are all stricter about the server-final signature. A per-driver interop matrix must exist before M3 is called done, or 'we added auth' becomes 'we broke Go and Java'.
- Storing a verifier makes it offline-crackable. That is fine for a 192-bit generated password and dangerous for a human-chosen one. If `fleet password set` ever accepts a weak password and writes its verifier to a shared bucket, the whole 'bucket read grants nothing new' argument collapses. Enforce a minimum entropy at set time (Neon uses 60 bits; use 128).
- One credential means one blast radius: it is always superuser, there is no read-only tier, and there is no per-application credential. A leaked connection string given to a frontend, a CI job, or an agent is total. The mitigation (a second read-only role) is blocked on per-connection session state, which does not exist yet.
- Rotation interacts badly with sleep durability: rolling a service to pick up a new secret drops the awake instance's unflushed writes. The reload-credential path avoids it, but any operator or script that reaches for `gcloud run services update` instead will lose data silently. The fleet CLI must refuse to roll without a preceding POST /flush.
- /wake stays unauthenticated by necessity, which makes it an unauthenticated cost lever — anyone can repeatedly cold-start an instance and drive object-store reads and CPU-boost billing. No rate limiting exists anywhere in the stack.
- HTTP Basic in a browser triggers a native credential prompt with no logout, so the console cannot reuse the instance credential for interactive sessions. That is why the fleet-console credential survives — but it also means two mental models persist in the docs no matter how the code is written, and the naming must do the work.
